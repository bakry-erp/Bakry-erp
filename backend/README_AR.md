# Bakry ERP API — Backend المنشآت والمزامنة والاشتراكات

## الحالة

إصدار API الحالي في هذا المصدر هو `9.0.0`. تعرض `/api/health` رقم النسخة ومسارات المصادقة، ويعرض `/api/auth/owner-login-status` فحصًا مباشرًا غير مخزّن لمسارات دخول المالك. تستخدم مسارات دخول المالك الثلاثة المعالج نفسه وحد المحاولات نفسه.

جلسات الدخول مستقلة: كل عملية دخول تصدر JWT بمعرّف جلسة `jti` فريد، ولا يؤدي دخول مستخدم أو جهاز آخر إلى إبطال الجلسات السابقة. انتهاء الجلسة أو تسجيل الخروج في تبويب لا يلغي جلسات الأجهزة الأخرى. عدد حسابات الموظفين يظل خاضعًا لحد المستخدمين في الاشتراك، وهو منفصل عن عدد الجلسات المتزامنة.

تتضمن الحزمة الآن عميلًا سحابيًا في `../js/cloud-sync.js` مربوطًا بطبقة `IndexedDB`، مع طابور عمليات دائم في المتصفح، ومزامنة دورية وفورية بعد التعديل، واكتشاف تعارضات المراجعة. كما توجد واجهة مالك النظام في `../owner.html` لإدارة أكواد التفعيل والاشتراكات.

**هذه ليست شهادة بأن خدمة Render الحية اجتازت اختبار الاتصال.** رابط العميل مضبوط تلقائيًا على `https://bakry-erp.onrender.com`؛ لا يحتاج المستخدم إلى إدخاله. لم يتم تشغيل ترحيل قاعدة بيانات الإنتاج أو نشر تغييرات إلى Render من بيئة التطوير هذه. يلزم فحص `/api/health` والتأكد من جاهزية المخطط قبل اعتبار الاشتراكات والمزامنة السحابية جاهزتين للإنتاج.

## متطلبات التشغيل

- Node.js 20 أو أحدث.
- PostgreSQL.
- متغيرات Render الموجودة: `DATABASE_URL` و`ADMIN_USERNAME` و`ADMIN_PASSWORD` و`JWT_SECRET`.
- `APP_ORIGIN` قائمة بالأصول المسموح بها مفصولة بفواصل. يتم تطبيع الرابط تلقائيًا إلى الأصل فقط؛ لذلك `https://bakry-erp.github.io/Bakry-erp/` و`https://bakry-erp.github.io` ينتجان الأصل نفسه. لا تستخدم `*`.
- لا تضع أي قيمة سرية داخل ملفات الواجهة أو مستودع GitHub.

## قاعدة البيانات — مهم قبل النشر

ملف `schema_subscription_v1.sql` ترحيل إضافي مستقل. لا تشغّله على قاعدة البيانات الحقيقية قبل:

1. أخذ نسخة احتياطية كاملة والتحقق من إمكانية استعادتها.
2. فحص الجداول والبيانات الموجودة فعليًا.
3. تحديد المنشأة المالكة للسجلات القديمة.
4. الحصول على موافقة صريحة على تنفيذ الترحيل.

الترحيل لا يحذف سجلات `app_records` ولا ينسبها تلقائيًا لأي منشأة؛ يترك `tenant_id` فارغًا. بعد مراجعة البيانات، توجد نقطة API إدارية تتطلب تأكيدًا صريحًا باسم `ASSIGN_NULL_TENANT_RECORDS` لنقل السجلات القديمة إلى منشأة محددة. لا تستدعِها قبل التأكد من أن جميع السجلات القديمة تخص هذه المنشأة.

## المسارات المتاحة في هذه المرحلة

### المالك

- `POST /api/auth/login` — مسار دخول المالك الأساسي باستخدام `ADMIN_USERNAME` و`ADMIN_PASSWORD`.
- `POST /api/owner/login` و`POST /api/auth/owner-login` — مساران بديلان متوافقان مع المسار الأساسي ويستخدمان نفس التحقق وحد المحاولات.
- `GET /api/auth/owner-login-status` — فحص مباشر غير مخزّن لمسارات دخول المالك وإصدار API.
- `GET /api/health` — فحص اتصال قاعدة البيانات وجاهزية الاشتراكات ورقم نسخة API ومسارات الدخول المنشورة.
- `POST /api/owner/activation-codes` — إنشاء كود تفعيل. يتطلب `duration` و`userLimit` صراحة. مدد الاشتراك: `month_1`, `month_2`, `month_4`, `year_1`, `lifetime`.
- `GET /api/owner/activation-codes` — عرض الأكواد وحالاتها دون إظهار الكود السري نفسه.
- `GET /api/owner/tenants` — عرض المنشآت والتراخيص وعدد الموظفين.
- `POST /api/owner/tenants/:tenantId/suspend` — إيقاف منشأة.
- `POST /api/owner/tenants/:tenantId/extend` — تمديد الاشتراك.
- `POST /api/owner/tenants/:tenantId/user-limit` — ضبط حد الموظفين لرقم موجب أو `"unlimited"`.
- `POST /api/owner/activation-codes/:codeId/cancel` — إلغاء كود لم يُستخدم بعد.
- `POST /api/owner/tenants/:tenantId/adopt-legacy-records` — نقل السجلات القديمة غير المنسوبة، ويتطلب `{ "confirm": "ASSIGN_NULL_TENANT_RECORDS" }`.

### المنشأة والموظفون

- `POST /api/license/activate` — استخدام الكود وإنشاء المنشأة وحساب Admin الأول. يلزم `code`, `tenantName`, `adminUsername`, `adminPassword`.
- `POST /api/auth/tenant-login` — دخول موظف المنشأة باستخدام `tenantSlug`, `username`, `password`.
- `GET /api/auth/me` — بيانات المستخدم والمنشأة الحالية.
- `GET /api/users` و`POST /api/users` و`PATCH /api/users/:userId` — إدارة حسابات الموظفين للـ Admin.
- `GET /api/license/status` — حالة الترخيص للتوكن الحالي.

### البيانات والمزامنة

- `GET /api/stores/:store` — قراءة سجلات المنشأة فقط.
- `POST /api/sync/batch` — استقبال دفعة عمليات مع `operation_uuid` لمنع التكرار و`base_revision` لكشف تعارض التعديلات.
- `POST /api/admin/data/clear` — مسح سجلات التشغيل (`app_records` و`sync_operations`) للمنشأة الحالية فقط. يتطلب توكن مدير منشأة صالحًا وكلمة مروره الحالية، ويُسجّل العملية في `license_audit_events`. لا يحذف حسابات الموظفين أو اشتراك المنشأة أو سجل التدقيق.
- يبدأ الوضع المحلي العمل دون جلسة سحابية. كل تغيير على الجداول المدعومة يُحفظ في `cloud_outbox` حتى يكون جاهزًا للرفع لاحقًا. عند تسجيل دخول سحابي ناجح إلى المنشأة، يرفع العميل العمليات المعلقة والصفوف المحلية الجديدة تلقائيًا قبل تطبيق لقطة السيرفر.
- عند وجود تعارض يرجع الخادم `409 sync_conflict` ولا يعتمد أي عملية من الدفعة المتعارضة؛ على العميل الاحتفاظ بالعمليات المحلية وحل التعارض قبل الإعادة.
- تتشارك المزامنة والمسح قفلًا استشاريًا خاصًا بالمنشأة حتى لا تُعاد كتابة السجلات بالتزامن مع عملية المسح.
- تشمل استجابة القراءة `deleted_at` ويستخدمها عميل المزامنة الحالي لمعالجة الحذف المنطقي.

## سياسة الاشتراك والقرارات غير المحسومة

- مدد الشهر والشهرين والأربعة أشهر تدعم إما `calendar` أو `30_days`، ولا يقبل الخادم إنشاء كود شهري دون تحديد السياسة.
- اشتراك السنة يحسب 12 شهرًا تقويميًا. الاشتراك الدائم بلا تاريخ انتهاء.
- `userLimit` مطلوب عند إنشاء كود: رقم موجب، أو النص `"unlimited"` إذا تقرر أن عدد الموظفين غير محدود. الخادم لا يخمّن قرار الباقة. إضافة الموظفين تُنفذ داخل معاملة مع قفل صف الاشتراك لمنع تجاوز الحد بطلبات متزامنة.
- التجربة 3 أيام يجب أن تظل بياناتها محلية في IndexedDB. لم يتم تشغيل مؤقت التجربة في الواجهة بعد؛ كما أن حفظ المؤقت محليًا وحده لا يمنع التحايل بمسح بيانات المتصفح.
- فترة السماح Offline وسياسة التحقق الدوري تحتاجان ربطًا واختبارات من جهة العميل قبل اعتماد سياسة تمنع الوصول.

## الاختبارات

من داخل مجلد `backend`:

```bash
npm install
npm test
npm start
```

اختبارات `npm test` الحالية تشمل استقلال جلسات JWT وتفرد معرّفات الجلسات، وانتهاء صلاحية التوكن والتحقق من سلامته، وحساب مدد الاشتراك وتقويم الشهور، واختبارات طابور المزامنة وتسلسل المراجعات وحماية السجلات عند استجابة سيرفر فارغة أو غياب عملية محلية من السيرفر. لا تغني عن اختبارات التكامل مع PostgreSQL أو اختبار تشغيل الواجهة على أجهزة فعلية.

## النشر

هذا الإصدار V9 لا يتضمن أي ملف ترحيل SQL ولا يحتاج إلى تغيير مخطط PostgreSQL. لا تشغّل `schema.sql` أو `schema_subscription_v1.sql` ضمن نشر V9. بعد رفع الملفات، انشر Backend عبر Render مع HTTPS وإعداد `APP_ORIGIN` الحالي، ثم اختبر `/api/health` و`/api/auth/owner-login-status` ودخول المالك. يجب أن يعرض `/api/health` قيمة `api_version: 9.0.0`، ويعرض فحص المالك `owner_login_ready: true` ومسارات تسجيل الدخول الثلاثة. احتفظ بنسخة احتياطية دورية من PostgreSQL كإجراء حماية عام. لم يتم تشغيل أي عملية مسح بيانات ضمن هذه التعديلات.
