# Bakry ERP / MotoMax — دليل النشر والتشغيل

## حالة الإصدار

تتضمن هذه الحزمة:
- واجهة المعرض وإدارة الصفحات مع تخزين محلي IndexedDB.
- طبقة مزامنة سحابية متعددة المنشآت والأجهزة في `js/cloud-sync.js`.
- Backend مبنيًا على Express وPostgreSQL، مع دخول المنشآت والمستخدمين وأكواد التفعيل والاشتراكات.
- واجهة إدارة الاشتراكات للمالك عبر `owner.html`.

وجود كود العميل والخادم لا يعني أن الموقع أصبح متصلًا بسيرفر إنتاج تلقائيًا. التفعيل الفعلي يتطلب إعداد Backend وPostgreSQL، وتشغيل الترحيل بعد نسخة احتياطية ومراجعة البيانات، ثم ضبط رابط API ونشر الواجهة.

## متطلبات السيرفر

- Node.js 20 أو أحدث.
- PostgreSQL.
- متغيرات بيئة: `DATABASE_URL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `JWT_SECRET`, `APP_ORIGIN`.
- `JWT_SECRET` عشوائي بطول 32 حرفًا على الأقل.
- `APP_ORIGIN` أصل الموقع فقط دون مسار فرعي، ويجب مطابقته لنطاق الواجهة.
- استخدام HTTPS للاتصال الخارجي.

مثال الإعداد موجود في `backend/.env.example`. لا تضع القيم السرية داخل HTML أو JavaScript أو GitHub.

## قاعدة البيانات — إجراء أمان إلزامي

ملف `backend/schema_subscription_v1.sql` ترحيل إضافي. لا تشغله على قاعدة الإنتاج قبل:

1. أخذ نسخة احتياطية كاملة واختبار الاستعادة.
2. فحص الجداول والبيانات الحالية فعليًا.
3. اختبار الترحيل على قاعدة Staging.
4. تحديد مالك السجلات القديمة ومراجعة العلاقات بينها.
5. الحصول على موافقة صريحة قبل ترحيل الإنتاج.

الترحيل لا يحذف السجلات القديمة ولا يسند `tenant_id` إليها تلقائيًا؛ تبقى السجلات القديمة غير منسوبة إلى منشأة حتى تتم مراجعتها. توجد نقطة إدارية منفصلة لتبني السجلات القديمة، وتتطلب نص تأكيد صريحًا، ولا ينبغي استدعاؤها قبل إثبات ملكية البيانات.

بعد الترحيل، افحص `GET /api/health` وتأكد أن `subscriptions_schema_ready` تساوي `true`.

## المزامنة السحابية

عند نجاح دخول المنشأة سحابيًا:
- تحفظ تغييرات IndexedDB محليًا أولًا، وتوضع في `cloud_outbox` حتى لا تضيع العمليات غير المرسلة.
- ترسل التغييرات إلى `POST /api/sync/batch`.
- تسحب الواجهة سجلات المنشأة عبر `GET /api/stores/:store`.
- يبدأ الإرسال بعد التعديل، مع مزامنة دورية كل 30 ثانية وعند عودة الاتصال.
- تستخدم مراجعات السجلات لاكتشاف التعارض؛ عند التعارض تتوقف العملية وتبقى البيانات المعلقة محفوظة بدل الكتابة فوق تعديل جهاز آخر.
- أول رفع لبيانات محلية قديمة إلى سيرفر فارغ يتطلب موافقة مدير المنشأة. لا تخلط بيانات محلية قديمة مع بيانات سحابية موجودة تلقائيًا.

لربط جهاز آخر، افتح `index.html`، اختر «الدخول السحابي»، ثم استخدم رابط API وكود المنشأة واسم المستخدم وكلمة المرور الخاصة بالمنشأة نفسها. يجب نشر API وقاعدة البيانات أولًا. لا يوجد ضمن هذا الإصدار ضمان Offline Grace Period مكتمل؛ تعذر الاتصال بالسيرفر عند استعادة جلسة سحابية قد يمنع الدخول السحابي حتى عودة الاتصال.

## إدارة الاشتراكات

افتح `owner.html` على نفس نطاق الواجهة لتسجيل دخول المالك وإنشاء الأكواد وعرض المنشآت وإيقافها وتمديد الاشتراك وتعديل حدود المستخدمين. بيانات المالك تؤخذ من متغيرات البيئة على السيرفر، ولا توجد كلمات مرور مالك مضمنة في ملفات الواجهة.

مدد الباقات: `month_1`, `month_2`, `month_4`, `year_1`, `lifetime`. الباقات الشهرية تتطلب تحديد `calendar` أو `30_days` صراحة. يجب تحديد حد المستخدمين كعدد موجب أو `unlimited`.

واجهة إدارة حسابات المستخدمين المتقدمة وسياسة التجربة المجانية وفترة السماح Offline تحتاج استكمالًا منفصلًا قبل اعتمادها تشغيليًا.

## واجهة الدخول والأمان

- «الوضع المحلي» مخصص لهذا الجهاز ولا يزامن البيانات تلقائيًا.
- كلمات مرور الوضع المحلي التاريخية ما زالت محفوظة داخل المتصفح، وقد تكون نصًا صريحًا؛ قفل المحاولات المحلي ليس بديلًا عن المصادقة السحابية.
- كلمات مرور حسابات المنشأة السحابية يتم تجزئتها على السيرفر باستخدام `scrypt`، مع رموز جلسات محددة الصلاحية وتحديد لمحاولات الدخول.
- لا تحفظ كلمات المرور داخل Local Storage، ولا تشارك حساب مدير المنشأة.

## واجهات API الأساسية

### المالك
- `POST /api/auth/login`
- `POST /api/owner/activation-codes`
- `GET /api/owner/activation-codes`
- `GET /api/owner/tenants`
- `POST /api/owner/activation-codes/:codeId/cancel`
- `POST /api/owner/tenants/:tenantId/suspend`
- `POST /api/owner/tenants/:tenantId/extend`
- `POST /api/owner/tenants/:tenantId/user-limit`

### المنشأة
- `POST /api/license/activate`
- `POST /api/auth/tenant-login`
- `GET /api/auth/me`
- `GET /api/license/status`
- `GET /api/stores/:store`
- `POST /api/sync/batch`

يوجد مسار إداري لمسح سجلات التشغيل في الخادم، لكنه ليس جزءًا من الإصلاح ولا ينبغي تشغيله دون طلب صريح، تحقق من الهوية، ونسخة احتياطية.

## الاختبارات

من داخل `backend`:

```bash
npm install
npm test
npm start
```

الاختبارات الحالية تغطي حساب مدد الاشتراك ومراجعات عمليات المزامنة والتعامل الآمن مع الطوابير وبعض حالات حماية السجلات. لا تغني عن اختبار التكامل مع PostgreSQL أو تجربة قبول على أجهزة فعلية.

## النشر المقترح

1. جهّز Backend وPostgreSQL في بيئة Staging.
2. انسخ قاعدة الإنتاج إلى Staging ثم جرّب الترحيل والاختبارات.
3. اختبر تفعيل منشأة تجريبية ودخول جهازين ومزامنة تغييرات متزامنة.
4. خذ Backup إنتاجي جديدًا وتأكد من الاستعادة قبل ترحيل الإنتاج.
5. انشر Backend واضبط متغيرات البيئة وHTTPS و`APP_ORIGIN`.
6. انشر ملفات الواجهة، ثم أدخل رابط API في شاشة الدخول السحابي.
7. ارفع البيانات المحلية القديمة من جهاز واحد فقط بعد تحديد النسخة الأساسية وأخذ نسخة احتياطية.
